## Install

Pick the binding for your runtime. This first run uses Python because it is
compact, but the durable behavior lives in the shared SQLite extension and
the repo also includes Node, Bun, Ruby, Go, and Elixir bindings over the
same contract.

```bash
pip install knockerlite
```

If you are not using Python, jump to [SQLite bindings](/reference/sqlite-bindings/)
for the equivalent open, receive, worker, operator, and retention shapes.

## Open a database and register an endpoint

```python
import knocker

webhooks = knocker.open("knocker.db")

stripe = webhooks.endpoint(
    "stripe",
    path="/webhooks/stripe",
    provider="stripe",
    secrets=["whsec_123"],
)
```

That gives you:

- a named endpoint row in SQLite
- Stripe signature verification using the active secret list
- provider-based extraction of the upstream event id and event type

## Register a handler

```python
@stripe.handle("checkout.session.completed")
def handle_checkout(event, tx):
    tx.query(
        "INSERT INTO handled_events (event_id, provider_event_id) VALUES (?, ?)",
        [event.id, event.provider_event_id],
    )
```

Handlers receive `(event, tx)`, not a raw request object. They run later against rows already committed to SQLite.

Writes through `tx` commit atomically with Knocker's `handled` transition and queue acknowledgement. Keep handlers synchronous, short, and DB-local; if you need outbound HTTP or slow work, enqueue an app-owned follow-up job from inside the transaction.

## Receive a webhook

In examples, `receive(...)` is shown directly. In a real app, call it from your existing HTTP route after reading the raw body bytes and headers.

```python
result = stripe.receive(
    body=b'{"id":"evt_1","type":"checkout.session.completed"}',
    headers={"stripe-signature": "..."},
)

assert result.status_code == 204
```

`receive(...)` verifies the request, stores a `Delivery`, and, when valid, creates or correlates a durable `Event`.

Knocker does not ship framework adapters; see [Framework integration](/guides/framework-integration/) for FastAPI, Starlette, Flask, and generic examples.

## Run the worker

```python
import asyncio

async def main():
    stop = asyncio.Event()
    worker = asyncio.create_task(webhooks.run_worker(stop_event=stop))
    try:
        await asyncio.sleep(10)
    finally:
        stop.set()
        await worker

asyncio.run(main())
```

The worker claims queued event jobs from Honker and dispatches them to your registered handlers. It can run in the same process as ingress or in a separate process that opens the same SQLite file.

`run_worker(...)` is a library primitive, not a daemon supervisor. In production, wrap it in your app's restart policy. You can inspect local process state with `webhooks.worker_states()` and pass `on_error=...` for worker-loop failures outside normal handler retry/dead-letter handling.

## Inspect what landed

```python
events = webhooks.list_events(limit=10)
deliveries = webhooks.list_deliveries(limit=10)
```

Use the operator surface to inspect durable state before you build any app-specific admin routes around it.
